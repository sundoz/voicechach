# Урок 0. Каркас бэкенда

Цель этапа: сервер, который ещё ничего не умеет по бизнес-логике, но уже
«взрослый»: конфигурируется, логирует, корректно падает и останавливается,
собирается в Docker и проверяется в CI. Всё остальное будем навешивать на него.

## 1. Cargo workspace

`Cargo.toml` в корне — это **workspace**: набор crate'ов с общим `Cargo.lock`
и общей папкой `target/`. Сейчас crate один (`crates/server`), позже появятся
`crates/voice` (SFU) и, возможно, `crates/protocol` (общие типы событий).

`[workspace.dependencies]` — версии зависимостей задаются в одном месте,
а crate'ы пишут `axum.workspace = true`. Так не бывает рассинхрона версий.

**Crate** = единица компиляции. У `server` есть и `lib.rs`, и `main.rs`:
- `lib.rs` — библиотека (вся логика). Её импортируют тесты: `use server::app`.
- `main.rs` — тонкая точка входа, которая только склеивает части.

Это стандартный приём: интеграционные тесты в `tests/` видят только
публичное API библиотеки, бинарник им недоступен.

## 2. Модули

`pub mod config;` в `lib.rs` говорит компилятору: «есть модуль `config`,
ищи его в `config.rs`». `routes/mod.rs` — модуль-папка с подмодулями.
`pub` — видимость: без него элемент виден только внутри своего модуля.

`crate::` — путь от корня текущего crate'а (`use crate::state::AppState`).

## 3. async и tokio

Rust сам по себе не содержит рантайма для async. `async fn` возвращает
**Future** — ленивое вычисление, которое ничего не делает, пока его не
`.await`-нут. Исполняет future'ы рантайм — у нас **tokio**.

```rust
#[tokio::main]           // макрос разворачивается в создание рантайма
async fn main() -> anyhow::Result<()> { ... }
```

Почему async для сервера: тысячи соединений (а у нас будут WebSocket'ы,
висящие часами) обслуживаются несколькими потоками ОС. Пока один запрос ждёт
БД, поток выполняет другие.

`tokio::select!` (см. `app.rs::shutdown_signal`) — ждёт несколько future
одновременно и продолжает с тем, что завершился первым. На этапе 3 это будет
главный инструмент в WebSocket-сессии.

## 4. Обработка ошибок: `Result`, `?`, `thiserror`, `anyhow`

В Rust нет исключений. Функция, которая может упасть, возвращает
`Result<T, E>`. Оператор `?` — «если `Err`, верни его из функции наверх
(сконвертировав через `From`), иначе распакуй `Ok`».

Два crate'а, два назначения:
- **`anyhow`** — для *приложения*, где ошибку нужно только залогировать
  (`main`, инициализация). `.context("...")` добавляет человеческое описание.
- **`thiserror`** — для ошибок, которые *обрабатываются*: каждый вариант
  `enum` значит своё. См. `error.rs`:

```rust
#[derive(Debug, thiserror::Error)]
pub enum AppError {
    #[error("not found")]
    NotFound,
    #[error(transparent)]
    Database(#[from] sqlx::Error),   // #[from] генерирует From<sqlx::Error>
    ...
}
```

Благодаря `#[from]` в хендлере можно писать `query(...).await?` — ошибка
sqlx сама превратится в `AppError::Database`.

А `impl IntoResponse for AppError` учит axum превращать ошибку в HTTP-ответ.
Это **трейт** — аналог интерфейса. Мы реализуем чужой трейт (из axum) для
своего типа, и axum начинает понимать `Result<Json<T>, AppError>` как ответ.

Обрати внимание: внутренние ошибки (500) логируются полностью, но клиенту
уходит только `"internal server error"` — детали БД наружу не отдаём.

## 5. Axum: роутер, хендлеры, экстракторы

Хендлер — обычная `async fn`. Её аргументы — **экстракторы**: axum по типу
аргумента понимает, что достать из запроса.

```rust
async fn ready(State(state): State<AppState>) -> AppResult<Json<Health>>
```

- `State(state)` — это pattern matching прямо в аргументе: распаковываем
  обёртку `State<AppState>` в переменную `state`.
- Позже будут `Json<T>` (тело), `Path<Uuid>` (параметр пути), `Query<T>`,
  и наш собственный `AuthUser` (этап 1).

`Router::new().nest("/health", health::router())` — роутеры собираются из
частей, как и модули. Каждый модуль `routes/*` отдаёт свой кусок.

## 6. Общее состояние и `Clone`

`AppState` передаётся в каждый запрос клонированием. Поэтому внутри должно
быть только то, что клонируется дёшево. `PgPool` внутри — `Arc` (счётчик
ссылок), клон = инкремент счётчика, а не новое подключение к БД.

Правило: тяжёлые общие вещи кладём в `Arc<...>`, изменяемые — в
`Arc<Mutex<...>>` или используем каналы (будет на этапе 3).

## 7. Middleware (tower)

axum построен на **tower**: middleware — это `Layer`, который оборачивает
сервис. В `app.rs`:

| Слой | Зачем |
|---|---|
| `SetRequestIdLayer` | каждому запросу UUID в `x-request-id` |
| `TraceLayer` | span с методом/URI/request_id — все логи внутри запроса помечены |
| `PropagateRequestIdLayer` | возвращает тот же id в ответе — клиент может сообщить его в баг-репорте |
| `TimeoutLayer` | запрос дольше N секунд обрывается |
| `CorsLayer` | разрешаем браузеру ходить к API с фронтенда |

## 8. Конфигурация (12-factor)

Конфиг не хардкодится и не лежит секретами в git. Слои (`config.rs`):
`default.toml` → `<APP_ENV>.toml` → переменные `APP__SECTION__KEY`.
В проде пароль БД придёт через `APP__DATABASE__URL`.

`#[derive(Deserialize)]` — **derive-макрос** serde генерирует код разбора
прямо из структуры. Опечатка в имени поля → ошибка при старте, а не в 3 ночи.

## 9. Логи: tracing

`tracing` — не просто логи, а **структурированные события и span'ы**:
`tracing::info!(%addr, "server started")` пишет поле `addr` отдельно.
Локально — читаемый вывод, в проде (`APP_ENV=production`) — JSON для
Loki/ELK. На этапе 7 те же span'ы уйдут в OpenTelemetry без переписывания кода.

## 10. Health checks

- `/health/live` — «процесс жив». Не трогает БД! Иначе при падении БД
  Kubernetes перезапустит все поды, и станет только хуже.
- `/health/ready` — «готов принимать трафик». Если БД нет — 503,
  балансировщик временно уберёт инстанс из ротации.

Поэтому пул создаётся через `connect_lazy`: сервер стартует без БД.

## 11. Graceful shutdown

При деплое оркестратор шлёт `SIGTERM`. `with_graceful_shutdown` перестаёт
принимать новые соединения и дожидается текущих запросов. Для WebSocket
это станет важнее: клиентов надо будет вежливо отключить, чтобы они
переподключились к новому инстансу.

## 12. Docker и CI

`Dockerfile` — multi-stage:
1. `cargo-chef` готовит «рецепт» зависимостей; слой с их сборкой кэшируется
   и пересобирается только при изменении `Cargo.toml`. Без этого каждая
   правка кода = пересборка всех зависимостей (минуты).
2. Финальный образ — `debian-slim` + один бинарник, запуск не от root.

CI (`.github/workflows/ci.yml`): fmt → clippy (`-D warnings`: предупреждения
= ошибки) → тесты с настоящим Postgres → сборка образа.

## Как запустить

```bash
cp .env.example .env
make deps            # Postgres + Redis в docker
make run             # сервер на :8080
curl localhost:8080/health/ready
make check           # то же, что в CI
```
